# Постановка: перенос метрик дашборда МирГПТ в Grafana

**Кому:** разработчику, который поднимает дашборд в Grafana.
**Что на входе:** рабочий HTML-прототип `design_handoff_mirgpt_dashboard/` и готовые SQL в `sql/all_queries.sql` + `sql/check_tiles.sql`.
**Что на выходе:** один дашборд в Grafana, повторяющий состав метрик прототипа, без CSV и ручных выгрузок.

---

## 1. Цель

Сейчас цикл такой: аналитик руками запускает SQL в DBeaver → экспортирует 6 CSV → загружает их в HTML-страницу через шапку. Обновление данных — ручная операция на каждый просмотр.

Нужно: те же метрики читаются Grafana напрямую из Postgres, период задаётся стандартным time-picker'ом, CSV-контур отключается.

**Не делаем:** новых метрик; редизайна; изменения схемы БД; алертинга в первой итерации (пороги — да, алерты — отдельно).

---

## 2. Целевая архитектура

- **Grafana** ≥ 10, datasource **PostgreSQL** (та же БД, что сейчас смотрит аналитик), пользователь **read-only**.
- Один дашборд, 6 rows — по группам прототипа.
- Дашборд хранится в репо как JSON (`grafana/dashboards/mirgpt.json`) + provisioning-конфиг datasource. Правки — через экспорт JSON в git, не только через UI.
- Переменные дашборда: `$skill` (мультивыбор из `skills.name`, значение `All` по умолчанию). Период — встроенный time-range, без кастомных переменных.

> Допущение: Grafana имеет сетевой доступ к боевому Postgres. Если доступа нет и остаётся только выгрузка — постановка меняется принципиально (нужен промежуточный сбор метрик), сообщите до старта.

## 3. Источник истины по SQL

Брать **`sql/all_queries.sql`** и **`sql/check_tiles.sql`** — в них актуальная схема после серии фиксов.

**`grafana/sql/01–05_*.sql` — устаревшие**, не использовать как есть: там psql-переменные `:'date_from'` и join `s.tenant_id = c.tenant_id` по колонке, которой в схеме нет (убрана в 90b6cea). Файлы либо переписать под Grafana, либо удалить.

Фактическая схема, на которую опираются рабочие запросы:

| Таблица | Поля, которые используются |
|---|---|
| `users` | `id`, `created_at`, `display_name` |
| `chats` | `id`, `user_id`, `system_prompt`, `created_at`, `message_count` |
| `messages` | `id`, `chat_id`, `role` (`user`/`assistant`), `created_at`, `token_count`, `feedback_vote` (`up`/`down`), `status`, `metadata` (jsonb: `llmMs`, `ragMs`, `ttftMs`) |
| `skills` | `name`, `category`, `system_prompt` |

## 4. Что переписать в запросах

Механическая, но обязательная часть — сейчас период зашит строками `'2026-04-01'::timestamptz AND '2026-12-31'`.

1. **Период → макросы Grafana.** Везде заменить хардкод дат на `$__timeFilter(m.created_at)`. Там, где нужна явная граница (окна WAU/MAU/stickiness, `AGE()` для порога power users) — `$__timeFrom()` / `$__timeTo()`.
2. **Убрать `NOW()`.** В `all_queries.sql` stickiness считается от `NOW()`, а не от конца периода — на исторических данных это даёт неверную цифру (диагностика 2 в `sql/verify_metrics.sql` про это же). В Grafana якорить на `$__timeTo()`.
3. **Time series → формат Grafana.** Для графиков по дням: колонка времени с алиасом `time`, группировка через `$__timeGroup(m.created_at, '1d', 0)`, сортировка по времени. Иначе панель не отрисуется.
4. **Проценты.** Grafana умеет `unit: percent (0-100)` и `percentunit (0.0-1.0)` — выбрать одно и привести все запросы к нему; сейчас часть значений в долях, часть в процентах.
5. **Расчёты из JS перенести в SQL.** Четыре плитки сейчас считаются на фронте (`dashboard-v2.js`), а не приходят из запроса — в Grafana для каждой нужен свой SQL:
   - `tokens / answer` = `SUM(token_count) / кол-во ответов`;
   - `GPU-sec / chat` = `AVG(llmMs)/1000 × ответов / чатов`;
   - `throughput` = `SUM(token_count) / общее llm-время в секундах`;
   - `skill coverage` = доля чатов, где `system_prompt` сматчился со `skills`.
6. **Фильтр `$skill`.** Добавить в запросы, где он осмыслен (активность, оценки, латентность): `AND ($skill = 'All' OR s.name IN ($skill))`.

## 6. Оформление панелей

- **Описания.** В прототипе у каждой плитки есть `data-tip` — развёрнутое объяснение метрики и нормы. Перенести текст один-в-один в `Panel description` (иконка «i» в углу панели). Это содержательная часть, не декоративная.
- **Пороги.** Значения из колонки «Порог» выше завести в `Thresholds` панели, чтобы цвет числа менялся так же, как в прототипе.
- **Единицы.** Латентность — `ms`, доли — `percent`, токены — `short`.
- **Цвета/шрифты прототипа не переносим** — используем стандартную тему Grafana. Дизайн-система из `README.md` относится к HTML-прототипу и в Grafana неприменима.

## 8. Критерии приёмки

- [ ] Дашборд открывается без ручных загрузок; смена периода в time-picker'е пересчитывает **все** панели.
- [ ] Все 30 показателей из §5 присутствуют; ни одна панель не показывает захардкоженное или мок-значение.
- [ ] На периоде `2026-04-01 — 2026-12-31` цифры Grafana совпадают с CSV-выгрузкой прототипа (расхождение допустимо только по stickiness — из-за починки `NOW()`; расхождение зафиксировать в комментарии к панели).
- [ ] Каждая плитка имеет описание и пороги.
- [ ] JSON дашборда и provisioning лежат в `grafana/`, `grafana/sql/01–05_*.sql` приведены в актуальное состояние или удалены.
- [ ] Запросы работают на read-only пользователе.

## 9. Открытые вопросы — снять до старта

1. **Доступ.** Grafana ходит в боевой Postgres напрямую или в реплику? Есть ли уже read-only роль?
2. **`feedback_vote`.** В данных `up`/`down` или `like`/`dislike`? Проверить диагностикой 1 из `sql/verify_metrics.sql` — запросы написаны под `up`/`down`.
3. **Таймзона.** Группировка по часам суток — по UTC или Europe/Moscow? В прототипе явной конвертации нет, в Grafana задаётся на уровне дашборда.
4. **D30 retention.** Выносим плитку или ограничиваемся D1/D7?
5. **Таблица пользователей с ФИО.** `display_name` в Grafana виден всем, у кого есть доступ к дашборду. Нужны ли ограничения по правам на эту панель?
6. **Судьба HTML-прототипа.** После запуска Grafana он выводится из эксплуатации или остаётся для оффлайн-шеринга (`share.js`)? От этого зависит, поддерживать ли CSV-выгрузки дальше.
